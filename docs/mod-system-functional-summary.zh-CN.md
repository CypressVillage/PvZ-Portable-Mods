# Mod 系统功能总结（重新开发参考）

## 1. 本文定位

本项目决定不再迁移旧 Mod 框架的实现，而是在最新上游基础上重新开发。
本文只整理旧系统的功能、使用场景与已知边界，不是新框架架构设计、开发计划或 API 稳定性承诺。

- 重建分支：`mod-rebuild`。
- 初始上游基线：`396f1c7fcf0507dcd1b79dc1ffad139eea2fb6ca`。
- 功能参考来源：旧项目 `main` 的 Mod 代码、文档及此前检查的工作区修改。
- 以下“旧系统支持”仅表示旧代码曾提供对应能力，不表示新分支已经实现，也不代表每种组合都有完整测试覆盖。
- 旧源码保留在原分支供查阅，不复制到重建分支；旧文档中的架构、接口签名和状态说明不作为新实现规范。

## 2. 核心使用场景

1. 玩家安装 Mod，在游戏内查看信息、管理启用状态和依赖。
2. 作者添加植物、僵尸、投射物和玩法模式，不必为每份内容修改游戏源码。
3. 作者通过脚本响应游戏事件，调整实体行为、关卡状态和交互。
4. 作者提供自定义图片、动画、声音资源或本地化字符串。
5. Mod 保存自己的配置和数据，不污染原版进度。
6. 作者用日志、示例和测试定位错误；错误信息能指出所属 Mod。

## 3. 旧系统的功能清单

### 3.1 安装、识别和依赖

- 从本地 Mod 目录发现内容包。
- 读取唯一标识、显示名称、作者、版本、描述、入口及必需依赖等元数据。
- 检查非法或重复标识、缺失依赖、不可用依赖链和循环依赖。
- 在满足依赖的前提下确定加载顺序；相同输入得到相同顺序。
- 持久化玩家的启用状态。
- 启用一个 Mod 时联动启用依赖，禁用一个依赖时联动禁用依赖者。

旧实现采用目录包、`mod.json` 清单和 Lua 入口。这是历史做法，不强制新系统使用相同包格式。

### 3.2 游戏内管理

- 在主菜单的选项中打开 Mod 管理器。
- 滚动浏览 Mod 列表、切换暂存的启用状态。
- 查看完整名称、元数据、依赖、错误和待生效状态。
- 应用或取消操作；无效 Mod 显示原因且不能启用。
- 在空闲主菜单整体重载 Mod，使部分变更无需重启生效。

旧工作区还包含重载预检、失败恢复配置及不可恢复时要求重启的保护逻辑；不能将它理解为任意运行时状态都可以回滚。

### 3.3 自定义植物

- 注册植物标识、名称、费用、冷却、发射间隔等属性。
- 复用原版动画，或提供外部 Reanim 和自定义图片。
- 在选卡、卡片显示、放置、预加载和图鉴中使用自定义植物。
- 响应生成、更新、攻击、死亡、被吃、产出、升级或变形等事件。
- 控制攻击、状态、睡眠、动画等行为。
- 使用可复用的状态机、自动射击、延迟动作和周期动作辅助逻辑。

旧系统的逐帧植物更新事件主要面向自定义植物，不应描述为已为所有原版实体提供通用逐帧扩展。

### 3.4 自定义僵尸

- 注册名称、生命值、移动速度、攻击伤害、身体状态和动画。
- 在指定行生成僵尸，查询和操作关卡内僵尸。
- 响应生成、死亡、攻击、进屋、冻结、黄油和魅惑等事件。

旧系统不支持安全注册自定义头盔和盾牌装备：装备依赖的动画轨道、附件与身体状态并未完整适配。

### 3.5 自定义投射物

- 注册伤害、速度和图片。
- 在指定位置与行生成投射物。
- 修改部分运动、伤害及追踪目标属性。
- 响应生成、命中和飞出屏幕等事件。

### 3.6 自定义玩法模式

- 注册显示名称和挑战界面入口。
- 基于一个原版模式的规则启动自定义玩法。
- 让脚本识别当前自定义模式，并响应关卡开始和结束。

旧系统不是完整的独立关卡或规则编辑器。自定义模式仍借用原版规则，不自动获得独立进度、成就、挑战记录或中途存档。

### 3.7 游戏状态与实体交互

- 查询模式、波次、总波数和昼夜、泳池、屋顶、雾等场景信息。
- 查询全部实体、按行查询、按格子查询与目标查找。
- 读取或调整阳光，生成阳光或金币，收集掉落物。
- 对实体造成伤害，查询距离，调整部分攻击或状态属性。
- 暂停游戏、调整游戏速度、播放已有音效、显示提示。
- 响应波次推进、旗帜波、小推车触发和阳光数量变化。

### 3.8 脚本事件与定时动作

- 提供 Mod 初始化、游戏开始、关卡开始和结束等生命周期事件。
- 提供植物、僵尸、投射物、掉落物和界面事件。
- 执行延迟或重复回调，并允许取消。
- 捕获并记录脚本异常；回调执行时识别所属 Mod。

脚本异常捕获不等于完整安全沙箱，也不意味着能阻止无限循环、过量资源使用或所有原生崩溃。

### 3.9 动画与资源

- 优先查找已启用 Mod 的资源，缺失时回退到基础资源。
- 提供图片、声音、动画及属性资源目录覆盖入口。
- 覆盖本地化字符串，注入自定义内容的名称和描述。
- 加载外部 Reanim；控制播放轨道、速率、进度、循环、位置、缩放及部分轨道可见性。

资源目录覆盖不等于已支持任意新音效注册。旧系统明确提供的是已有音效播放和资源路径覆盖。
已缓存的原版资源不保证随 Mod 重载刷新，部分改动仍要求重启。

### 3.10 自定义界面

- 创建模态或非模态对话框。
- 添加按钮、按钮回调和静态标签，修改标题与正文，关闭对话框。
- 在关卡内添加、移除、隐藏或修改简单按钮，并响应点击。

旧系统不提供通用界面布局编辑器或完整控件脚本绑定。

### 3.11 数据持久化

- 按 Mod 标识隔离保存字符串键值数据。
- 独立保存全局启用配置。
- 对写入错误和无效数据提供保护或错误报告。
- 避免自定义模式写入原版进度与中途存档槽。

旧实现的普通中途存档仍可能包含动态实体的数字类型；更改启用列表或注册顺序后，恢复这些引用并不可靠。

### 3.12 作者工具与示例

- 日志输出和清晰的加载、依赖、注册、回调错误。
- 自动收集阳光示例。
- 自定义植物状态机与多发射击示例。
- 自定义植物、投射物、图片和原版动画组合示例。
- 速度控制、关卡按钮与数据持久化示例。
- 植物行为辅助功能测试，以及清单、依赖、配置、存档和脚本校验测试。

## 4. 旧系统的限制：不要原样继承为产品要求

- 所有 Mod 共享脚本全局环境，普通变量和函数可能相互污染。
- 不支持依赖版本约束、可选依赖或引擎/API 版本兼容性门控。
- 加载优先级只是顺序，不是完整的内容冲突、替换和覆盖协议。
- 重复内容标识被拒绝，不能据此推断已有可组合的原版内容修改机制。
- 不支持关卡运行中重载或单个 Mod 安全卸载。
- 整体重载会丢失脚本临时状态，部分缓存资源仍需重启刷新。
- 没有实现 JSON 植物、僵尸、模式或投射物数据表，也没有实现 `strings.json`。
- 自定义模式、装备系统、存档恢复和界面扩展都有上述边界。
- 跨平台是目标，不是旧实现全平台已验证的事实；旧 Lua-enabled WASM 构建明确不受支持。
- 旧测试只覆盖部分模块，不能用测试通过代替完整引擎与交互验证。

## 5. 重建时需要重新决定的问题

以下仅列出功能层面的开放问题，不在本文确定技术方案或开发顺序：

- 首版支持哪些场景、平台和内容类型？
- 是否继续使用 Lua；是否需要每 Mod 隔离、权限和资源预算？
- 内容标识如何跨安装、加载顺序与存档保持稳定？
- 是否支持修改原版内容，多个 Mod 冲突时由谁裁决？
- 依赖、版本、引擎兼容性以及错误降级应如何向玩家解释？
- 启用、禁用、更新后何时生效；是否先明确要求重启，再考虑重载？
- Mod 存档是否需要版本迁移；缺少 Mod 时如何处理已有存档？
- 自定义模式是否需要独立规则、关卡、进度和成就？
- 哪些脚本接口允许改变游戏状态，哪些仅供查询？
- 作者需要哪些调试、测试、文档和示例支持？

## 6. 不强制兼容的历史细节

重建不默认保留旧 C++ 类与文件布局、全局对象、回调名称、Lua API 签名、数字 ID 区间、清单格式、帧计时方式或旧脚本直接运行能力。
应先确定要提供的功能与安全边界，再选择适合最新上游的实现；旧代码仅作为行为与需求参考。
